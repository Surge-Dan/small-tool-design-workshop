# 设计引擎：从产品任务到视觉原型

这份参考只在需要设计方法、视觉方向或高保真原型时读取。目标是把用户的任务翻译成一套有依据的界面，而不是先套一个风格。

## 1. 先判断输入是否足够

- 用户只有主题或一句模糊想法：只问影响玩法的高价值问题，最多 3 个；也可以先给一个最小方向供用户修正。
- 用户给了目标、流程或参考图：直接设计，不重复访谈。
- 用户说“直接做”：采用低风险默认值，明确假设，直接进入原型。
- 用户要求局部修改：保留已确认的流程、颜色、文案和状态，只改指定范围。

## 2. 用一句话定义产品任务

用下面的句式压缩需求：

> 用户在什么场景下完成什么动作，并获得什么结果或情绪。

如果这句话仍然只能写成“做一个好看的工具”，说明需要引导；不要用装饰替代产品命题。

## 3. 判断体验骨架

从测试、分析、生成、计算、推荐、编辑、游戏化中选择最接近的一类。它决定核心路径和结果结构，但不决定外观。

先画最短路径：

```text
入口 → 核心动作 → 反馈或结果 → 结束动作
```

只有会影响核心路径的状态才加入原型：未选择、处理中、结果、返回、重试。不要为了“完整”把所有异常都做成页面。

## 4. 从产品语义提炼设计方向

把主题拆成对象、动作、材质、情绪和场景，再选择一个能贯穿全局的视觉签名：

- 日记、记录、手册：日期、页边、横线、批注、纸张层级；
- 抽取、揭晓、测试：翻页、抽签、揭示顺序，但只保留一个揭示动作；
- 衣柜、搭配、收藏：档案、挂件、标签、物件关系；
- 计算、测量、对比：刻度、输入仪表、单位和结果变化。

如果主题是笔记本或手册，优先让“日期—标题—内容—记录动作”组成页面结构。不要先做一个 Hero，再把笔记本纹理贴上去。

## 5. 形成轻量设计系统

写 HTML 前先确定：

- 4～6 个有语义的颜色，而不是随机渐变；
- 标题、正文、辅助信息三种文字角色；
- 内容宽度、留白、密度和对齐方式；
- 选择、按钮、输入、结果和提示的最小组件集；
- 一个视觉签名和一个主要动效。

用“这个选择服务了什么任务”解释设计。解释不成立的颜色、标签、装饰和动画删掉。

## 6. 三遍原型法

1. 结构遍：先让用户走通核心路径，确认信息层级和按钮行为；
2. 视觉遍：把主题语义落实到材质、字级、颜色、版式和结果卡；
3. 节奏遍：只补必要的反馈、切换、结果揭示和保存动作。

每遍结束都做一次“换主题测试”：如果换掉主题后页面仍然完全成立，主题转译不够；如果删掉装饰后任务仍然成立，优先删装饰而不是加更多。

## 7. 文案密度和页面职责

引导文字不是默认配置。根据用户的熟悉度和任务风险决定：

- 选择题、轻记录、单一生成：短标题 + 直接操作即可；
- 新规则、复杂输入、危险操作：补充必要说明；
- 结果页：必须有结论和可理解的依据，不能只放一个漂亮标签。

一个页面只保留帮助用户完成当前动作所需的文字。删掉“给今天一点位置”“翻开就知道了”这类无法改变操作的句子。

## 8. 原型输出

默认交付一个可直接打开的单 HTML：内嵌 CSS/JS、移动端优先、本地模拟数据、稳定结果、主要按钮可操作。原型说明只需写设计命题、核心流程、已实现交互和关键假设。
